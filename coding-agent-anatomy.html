プロンプトを投げてから回答が終わるまで、
「ハーネス」と「API」の間で実際に何が起きているのか？

Coding Agent の正体は「賢いLLM」単体ではありません。あなたのMac上で動くローカル実行基盤（Harness: cortex プロセス）が、プロンプトにシステム指示・Skill・54個のツール定義スキーマを束ねて Snowflake の /api/v2/cortex/agent:run へ HTTPS POST し、SSEストリームで返ってくる tool_use 指示をインターセプトしてローカルで実行し、その結果を「擬似的な user メッセージ（tool_result）」として再びAPIへPOSTし直す while ループそのものです。

1回のユーザープロンプト ＝ N回の HTTPS POST 往復 (Iteration 1..N) ＋ ローカル権限ゲート (PermissionManager) ＋ ローカルOS / SQL実行

1. どこまでがローカルMacで、どこからがSnowflake Cloud APIか？（4つの境界線）

最重要ポイント：クラウド上のLLMはあなたのMacのファイルやシェルに直接触れません。JSONで「呼びたいツール名と引数」を返すだけです。

3. ここが分かるとすべて腑に落ちる！Coding Agent 5つの内部メカニズム

単なるチャットAPI呼び出しと決定的に違う技術ポイント

01 クラウドへ送るのは「ツールのJSON定義」だけ、実行は100%ローカル

APIリクエストの tools[] には、54個のツールの名前・説明文・引数JSON Schemaしか入っていません。LLMは「sql_execute をこのSQL文字列で呼んでくれ（client_side_execute: true）」というJSON片をSSEで返すだけで、実際のDB接続やファイル編集はすべて手元のハーネスが行います。

LLMの出力 = 単なる構造化データ {"type":"tool_use","name":"edit","client_side_execute":true}
実際にファイルを書き換える主体 = Mac上の cortex ハーネスプロセス

02 ツール実行結果は「人間になり代わった role: "user"」で返送される

LLMのAPI仕様上、assistant の tool_use に対する返答は role: "user" メッセージの中に type: "tool_result" ブロックを入れて返す決まりになっています。そのため .history.jsonl を見ると、あなたが何も打っていなくても assistant と user (tool_result) が何十往復も記録されます。

{"role":"assistant","content":[{"type":"tool_use","tool_use":{"tool_use_id":"toolu_01A",...}}]}
{"role":"user", "content":[{"type":"tool_result","tool_result":{"tool_use_id":"toolu_01A",...}}]}

03 なぜ「承認待ち」で完全に時が止まるのか？

LLMが tool_use を出力した時点で、1回目のHTTPレスポンス（SSEストリーム）はすでに完了して切断されています。ハーネスがローカルの await permissionManager.confirm() で一時停止しているため、あなたが Approve を押さない限り2回目のHTTP POST自体が永久に送信されません。

// 承認待ちの間、クラウド側では何も動いていない（クレジット消費もゼロ）
const decision = await permissionManager.requestUserApproval(toolCall); // ← ここでブロック！

04 サブエージェント (task) は「別スレッド・別コンテキスト」の独立ループ

ファイルを20個読む探索を親ループで直接やると、tool_result だけでコンテキスト枠が埋め尽くされます。task(subagent_type: "explore") を呼ぶと、ハーネスは別の subagentSessionId と専用スレッドで子ループを回し、最終レポート文字列だけを親の tool_result 1個に圧縮して返します。

親コンテキスト消費 = 子エージェントの最終要約（数KB）のみ！
子の試行錯誤（数十回の grep / read）は親のトークン枠を汚さない

05 Snowflake Thread キャッシュ (thread_id) と SQL 専用子セッション (RSS) の分離

CoCo は毎回全履歴をゼロから再送するのではなく、Snowflake側の /api/v2/cortex/threads/<thread_id> に会話スレッドを保持し、差分メッセージだけを agent:run に積みます（ログの lastSyncedHistoryLength）。さらに sql_execute ツールはエージェントAPIとは別の Restricted Session Scope (RSS) 子セッション上でクエリを実行するため、クエリ結果が巨大でもハーネス側でサマリー＋ファイル退避してから安全に次の POST へ渡せます。
